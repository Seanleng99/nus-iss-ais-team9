# Chinese language support

Coach uses one agent workflow, one set of financial tools and one set of ownership checks for English and Simplified Chinese. Language selection and reviewed fixed messages live in the shared `coach-i18n` package under `apps/shared`. Adding another language should extend that package's catalogs, recognition resources and acceptance cases, rather than copy agents or financial calculations.

The supported response locales are `en` and `zh-Hans`. The Coach language selector can explicitly choose either, and the `/api/coach` request accepts an optional `response_locale`. Legacy labels such as `English`, `Chinese` and the profile's `Mandarin` preference normalize to those tags. Unsupported explicit request locales are rejected. Unsupported profile preferences fall back to detection and then English. Traditional Chinese input examples and security patterns remain recognized, but a separate Traditional Chinese output catalog is not provided.

Selection order is an explicit language instruction in the current message, the Coach/API selection, the most recent explicit language instruction in backend-owned recent user dialogue, the saved profile preference, and finally bounded script detection. For example, an English question requesting Chinese receives Chinese; a Chinese question requesting English receives English. Kana and Hangul prevent the Han-character fallback from treating typical Japanese or Korean messages as Chinese. Short ambiguous text and unsupported languages are not reliably identified by this bounded detector.

The backend resolves the locale using owned conversation history and the persisted profile, then forwards it to AI. Each restricted specialist task receives only the selected locale alongside its existing context. Router, specialist, synthesis and compliance prompts use the same language. Existing `response_language` audit values remain `English` or `Chinese` for compatibility; `response_locale` records the selected tag. Historical blocked-response audit values retain their strict validation rules.

Fixed evidence gaps, refusals, income-memory replies, provenance labels and disclaimers use keyed JSON catalogs. Safety refusals remain exact reviewed templates; blocked model drafts are never translated into publishable content. Generated explanations use the existing multilingual model with the chosen output language and the same citation, evidence and safety validation. Retrieval continues to use canonical topic identifiers; educational aliases and Chinese topic labels now live in a vocabulary resource. Calculation results and database operations remain independent of language.

Chinese text and Han Unicode escapes are confined to JSON resources and datasets. Output messages live in `locales/zh-Hans.json`. Bilingual input and safety patterns live in `data/input_patterns.json`, intent terms and ordinal mappings in `data/input_vocabulary.json`, and script ranges in `data/scripts.json`. Code reads these resources through shared helpers without duplicating agent logic. Input rules recognize all supported languages regardless of the selected output locale, so choosing English cannot disable Chinese safety checks. Template patterns interpolate only application-owned regex fragments, preserving quantifiers and capture groups.

Independent Chinese test inputs and golden assertions live in each service's `tests/fixtures/language_cases.json`; evaluation questions remain in JSONL datasets. They are not loaded from production translations, so regression tests can detect a broken translation or rule. These patterns supplement shared permissions and safety validation; translating keyword lists is not sufficient to certify another language. Offline provider examples are resource data and do not establish live-model language quality. Developer documentation is in English.

The response selector controls Coach answers, not the language of every application page. Existing backend handlers that compose English transaction, budget or goal-management receipts are not all localized by this refactor. Their fixed text should be added to reviewed message catalogs before claiming complete Chinese coverage for every local workflow. Locale formatting, a Traditional Chinese catalog and additional languages are separate extensions. Live-model Chinese acceptance must still pass the existing evaluation gates.

Install the shared package with each service, for example `pip install -e apps/shared -e "apps/ai-service[dev]"` from the repository root. Container builds and CI install the package explicitly and include its JSON resources. Shared-package changes select all services in the CI/CD change classifier.

Run `python scripts/scan_chinese.py --output docs/chinese-character-inventory.json --markdown docs/chinese-character-inventory.md --check-code` to scan every tracked and non-ignored project text file. The inventory records file paths and literal/Unicode-escape line numbers without copying source contents. `--check-code` fails if Python, JavaScript, TypeScript or shell code contains Han literals or escapes; CI runs this check on every code change. Binary files, ignored environments and generated artifacts are excluded. Use `--revision HEAD` without `--check-code` and with an output under `artifacts/` to inspect the pre-change Git snapshot. See [the inventory summary](chinese-character-inventory.md) and [all matching line numbers](chinese-character-inventory.json).
